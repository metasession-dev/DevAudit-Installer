# feature-e2e.yml's REQ detection requires a literal `REQ-[0-9]+` in the branch name — off-convention naming silently skips feature-stage E2E verification

## Background

`feature-e2e.yml` (installer#174 / DEVAUDIT-003) exists specifically to run the E2E
specs tagged with a PR's REQ on PRs to the integration branch, uploading stage-2,
`origin=feature` evidence — "so regression-tier bugs surface during the feature
execution instead of at the release gate" (its own docstring). It's the mechanism
that's supposed to give CI-independent proof that a REQ's E2E coverage actually
passes, before merge.

Its detection step:

```bash
BRANCH="${{ github.head_ref }}"
if [[ $BRANCH =~ (REQ-[0-9]+) ]]; then
  REQ_ID="${BASH_REMATCH[1]}"
  ...
  if grep -rl "@requirement $REQ_ID" e2e/ --include="*.spec.ts" >/dev/null 2>&1; then
    echo "has_tests=true" >> "$GITHUB_OUTPUT"
  else
    echo "has_tests=false" >> "$GITHUB_OUTPUT"
  fi
else
  echo "req_id=none" >> "$GITHUB_OUTPUT"
  echo "has_tests=false" >> "$GITHUB_OUTPUT"
fi
```

The regex requires the literal, case-sensitive pattern `REQ-` (hyphenated,
uppercase) immediately followed by digits, anywhere in the branch name. If it
doesn't match, `has_tests` is unconditionally `false` and the actual test-execution
job (`run-feature-e2e`, gated on `needs.detect-req.outputs.has_tests == 'true'`) is
skipped — silently. The workflow itself still reports `success` (a skipped
dependent job doesn't fail the workflow run), so nothing in the PR's check list
signals that verification didn't happen.

## What happened

Neither of REQ-095's own branches (issue #603) matched this pattern:

- `fix/603-business-day-report-ranges` (original PR #604) — uses the *issue*
  number, no `REQ-` token at all.
- `fix/603-req095-post-merge-regression-fixes` (follow-up PR #606) — uses the
  issue number plus `req095` (lowercase, no hyphen between `req` and `095`).

On PR #606, this meant the newly-authored, `REQ-095`-tagged E2E spec
(`daily-report-business-date-selection.spec.ts`) was **never executed by CI at
all** — `detect-req` resolved `has_tests=false`, `run-feature-e2e` was skipped,
and `gh pr checks` showed the workflow as passing regardless.

The gap was invisible from the PR's check list. It only surfaced by cross-checking
the actual GitHub Actions run list against the DevAudit portal's database
directly: 6 screenshot evidence rows for REQ-095 *did* appear in
`compliance_evidence` — but those were PNGs generated by local test runs and
committed as binary files; the CI step that uploads per-REQ evidence uploads
whatever exists on disk tagged to an in-scope REQ (via commit `Ref: REQ-XXX`
trailers), regardless of whether *this* CI run produced them. `compliance_releases`
still showed the release in `draft`, and `compliance_release_checks` still showed
`skipped` for "E2E Regression (REQ-095)" — because that workflow only triggers on
PR-to-`main` or production deploy, never on this PR-to-`develop`. So the portal's
own state was internally consistent and honest; it was the *absence* of any
CI-attested pass that was easy to miss without deliberately checking for it.

## Root cause

Same class of gap as `docs/issues/e2e-gate-verifies-recency-not-relevance.md`
(installer#578) and `e2e-gate-enforcement-gap.md` (installer#226): a real,
functioning CI mechanism that is silently bypassable by an unremarkable, plausible
choice (here, a branch name) that nothing validates or warns about. The framework's
own playbooks reference `feat/REQ-XXX-*` / `fix/REQ-XXX-*` as the canonical branch
shape, but nothing enforces it, and the very first REQ-095 branch — produced by an
earlier `sdlc-implementer`/Codex session under this same framework — didn't follow
it either. Branch naming is a human/agent convention, never validated; commit
`Ref: REQ-XXX` trailers, by contrast, are *already* commitlint-enforced for every
`feat`/`fix`/`refactor`/`perf` commit and validated again in CI by
`validate-commits.sh` — making them the actually-reliable source of REQ-scope this
workflow should have used from the start.

## Proposed solutions

### Option A — Loosen the regex
Accept case-insensitive, hyphen-optional variants (`req[-_]?(\d{3,})`), normalizing
to `REQ-<n>`.

- **Rejected as the primary fix** — still depends on branch naming, which is
  unenforced and already demonstrated (twice, on the same REQ) not to reliably
  happen. Loosening the pattern only shrinks the miss rate, not eliminates the
  dependency.

### Option B — Derive REQ scope from commit trailers, not the branch name (recommended)
`compliance-evidence.yml`'s E2E-regression job already derives in-scope REQs
authoritatively this way (`git log --grep "Ref: REQ-XXX"` over the relevant commit
range) precisely because branch names aren't reliable. `feature-e2e.yml`'s
`detect-req` step should do the same: scan the PR's commits (`origin/<base>...HEAD`)
for `Ref: REQ-XXX` trailers (or `[REQ-XXX]` in the subject), dedup, and use that as
the REQ scope — falling back to the branch-name regex only as a secondary, best-effort
signal if no commit yields a trailer (e.g. a docs-only or pre-commitlint-era commit).

### Option C — Fail loudly when no REQ can be determined at all
Independent of A/B: if neither commit trailers nor the branch name yield a REQ,
post a visible `::warning::` (or PR comment) naming the branch and the commits
checked, instead of a silent `has_tests=false`. This is defense-in-depth for the
genuinely-untagged case, not a replacement for B.

## Recommended approach

**B + C.** Commit-trailer scanning removes the dependency on an unenforced naming
convention entirely and is consistent with how the rest of the framework already
establishes REQ-scope. C ensures that if a PR genuinely has no derivable REQ (e.g.
a rare non-conforming commit), that fact is visible on the PR rather than a quiet,
indistinguishable-from-normal skip.

## Required changes

1. **`sdlc/files/ci/feature-e2e.yml.template`** (or wherever this workflow is
   templated for `devaudit install`/`devaudit update`) — replace the `detect-req`
   step's sole reliance on the branch-name regex with commit-trailer scanning
   first, branch-name regex as fallback.
2. Add the visible-warning step from Option C when no REQ is found by either method.
3. **`release-playbooks/high-risk-release.md`** and other playbooks referencing
   `feat/REQ-XXX-*`/`fix/REQ-XXX-*` — note that branch naming is now advisory/
   cosmetic for this mechanism once commit-trailer detection ships, so operators
   don't keep treating it as load-bearing.
4. Regenerate/propagate to consumer repos via `devaudit update`.

## Acceptance criteria

- [ ] A PR from a branch named like `fix/603-req095-...` (no `REQ-` token) whose
      commits carry `Ref: REQ-095` trailers still resolves `has_tests` correctly
      and runs the tagged spec.
- [ ] A PR whose commits carry no `Ref: REQ-XXX` trailer and whose branch name
      also doesn't match gets a visible warning, not a silent skip.
- [ ] Existing correctly-named branches (`feat/REQ-XXX-*`) continue to work
      unchanged.
- [ ] Test: branch `fix/603-req095-x` with `Ref: REQ-095` commits, and REQ-095 has
      a tagged spec → job runs and uploads stage-2/origin=feature evidence.
- [ ] Test: branch `some-random-name` with a `Ref: REQ-999` commit trailer, and
      REQ-999 has a tagged spec → job still runs (proves branch-name independence).
- [ ] Test: no derivable REQ by either method → visible warning posted, workflow
      still completes (doesn't hard-fail the PR over this alone).
