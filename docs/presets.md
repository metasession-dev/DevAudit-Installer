# Onboarding presets

> Generated from `core/src/presets.ts` by `cli/tools/generate-presets-doc.mjs` (run `npm run docs:presets` in `cli/`). Do not edit this file by hand: change the data and regenerate. A test fails when the two differ.

A preset is a ready-made answer to the onboarding questions. `devaudit install` and `devaudit configure` offer the presets that fit your repository, show the whole resulting configuration in plain words, and let you change any one item. There are four presets and `custom`.

| Preset | For | Before a merge to the release branch | After deploy | Nightly | Who approves |
| --- | --- | --- | --- | --- | --- |
| **A** Solo, fast feedback | One developer who approves their own releases and wants quick feedback, with the gap recorded. | no regression gate; approval only | the release completes by itself | off | the author, gap recorded |
| **B** Safety net | A solo developer or small team that wants the important journeys tested before every release and the full pack run after it. | the critical tests block | the full pack once | 02:00 UTC | the author, gap recorded |
| **C** Team with a compliance lead | A team where someone other than the author approves every release and the whole test pack is a gate. | the full tests block | the full pack once | 02:00 UTC | a different person |
| **D** Full gate, tested once | The same team as C, with the full pack run once, before merge, and not again after the deploy. | the full tests block | nothing more | 02:00 UTC | a different person |

**custom** (always offered): You choose each setting yourself. This is also the path when no preset can be offered.

## The five moments

| Moment | Workflows |
| --- | --- |
| 1. Feature pull request opened | ci.yml Quality Gates (smoke is Gate 4); feature-e2e.yml |
| 2. Merged to the integration branch | ci.yml (push): the gates again, registers the release, uploads evidence |
| 3. Release pull request opened | check-release-approval.yml, compliance-validation.yml, e2e-regression.yml (pull_request) |
| 4. After approval and deploy | post-deploy-prod.yml; e2e-regression.yml (deployment_status); production review in the portal |
| 5. On a timer | e2e-regression.yml (schedule); periodic-review.yml (quarterly, always) |

True for every preset: smoke runs at moments 1 and 2 and blocks (Quality Gates is the required check); feature tests run at moment 1 only, when the branch names a requirement and a test is tagged for it, and do not block; the approval gate at moment 3 is always on; production evidence is collected at moment 4; the quarterly review runs at moment 5. With `e2e_regression_enabled: false` there is no `e2e-regression.yml`, so the critical and full groups never run automatically.

## Which preset is suggested

Scan, install and doctor use one rule. Only a preset that fits your repository can be suggested; when the rule names one that cannot be offered, the next one down (C, B, A) that can is suggested, and when none can, `custom`. Preset D is never suggested: it is chosen on purpose.

1. No smoke tests found: **A**.
2. You need evidence for SOC 2 or ISO 27001 and a full test pack exists: **C**.
3. You need evidence for SOC 2 or ISO 27001 but no full test pack exists: **B**.
4. Critical or full tests exist: **B**.
5. Otherwise: **A**.

When the portal's approval policy is unknown (a scan makes no portal call) A and B may be suggested with the note "needs portal support for a solo approver". C and D are shown with "needs a second portal admin". When C is suggested, the reason adds that D is the same without the full regression after deploy.

## Preset A: Solo, fast feedback

One developer who approves their own releases and wants quick feedback, with the gap recorded.

### What it writes

| Key | Value |
| --- | --- |
| `onboarding_preset` | `A` |
| `e2e_regression_enabled` | `false` |
| `approval.mode` | `solo_with_gap` |
| `release_branch_required_reviews` | `0` |
| `production_review.terminal_status` | `released` |
| Portal approval policy (tier B, interactive only) | `self_allowed_with_gap` |

It does not write `release_gate_tier`, `post_deploy_full_regression`, `scheduled_full_regression`; switching to it removes them.

### What runs when

| Moment | What happens |
| --- | --- |
| 1. Feature pull request opened | Smoke tests run and block the merge; the feature tests report. |
| 2. Merged to the integration branch | Smoke tests run and block. |
| 3. Release pull request opened | Approval only; no regression run. |
| 4. After approval and deploy | Production evidence is collected and the release completes automatically. |
| 5. On a timer | The quarterly review. |

### Evidence and gap

- **Evidence produced:** An approval record per release; smoke and feature results per change; the quarterly review.
- **Gap carried:** No segregation of duties; no full-regression evidence; no human production confirmation.
- **Clauses with a recorded gap:** `SOC2.CC8.1`, `ISO27001.A.8.32`. You approve your own releases. DevAudit records this as a control gap for SOC 2 CC8.1 and ISO 27001 A.8.32; an auditor will ask for a compensating control.

### What it needs

- a portal that allows a solo approver (the project approval policy `self_allowed_with_gap`)

### What runs when

| Moment | What happens |
| --- | --- |
| 1. Feature pull request opened | Smoke tests run and block the merge; the feature tests report. |
| 2. Merged to the integration branch | Smoke tests run and block. |
| 3. Release pull request opened | The critical tests run and block (smoke if there are no critical tests, and the summary says so); approval by the author. |
| 4. After approval and deploy | Production evidence; the full regression runs once (recorded, does not block); a person confirms production. |

### Evidence and gap

- **Evidence produced:** Preset A plus the critical results before every release, the full results per deploy and per night, and a human production confirmation.
- **Gap carried:** No segregation of duties; the full regression detects problems after release rather than preventing them.
- **Clauses with a recorded gap:** `SOC2.CC8.1`, `ISO27001.A.8.32`. You approve your own releases. DevAudit records this as a control gap for SOC 2 CC8.1 and ISO 27001 A.8.32; an auditor will ask for a compensating control.

### What it needs

- a portal that allows a solo approver (the project approval policy `self_allowed_with_gap`)
- smoke tests (critical tests are optional)

### What it needs

- a full test pack
- the project is shown with "needs a second portal admin" (a different person approves, and approving needs the admin role)

- the project is shown with "needs a second portal admin" (a different person approves, and approving needs the admin role)

## What a recorded gap means

Once the portal's approval policy exists, `SOC2.CC8.1` and `ISO27001.A.8.32` are satisfied only by an approval made by someone other than the release's creator or submitter. Under presets A and B (policy `self_allowed_with_gap`) they show as not covered after a self-approved release; under presets C and D (policy `independent`) they show as covered. Reports measure evidence readiness; they never say a project is compliant.

## Changing later

- `devaudit configure` with no arguments asks the questions again with your current answers as defaults, and shows a before and after summary.
- `devaudit configure set <key> <value>` changes one setting.
- `devaudit doctor` reports when the configuration no longer matches the preset you chose, and `devaudit doctor --guided` walks you through each gap.
- A project onboarded before presets existed has no `onboarding_preset`, which means `custom`: it is never moved onto a preset unless you choose one.
